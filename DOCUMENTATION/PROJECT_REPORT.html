Executive Summary
FoodRescue is an end-to-end full-stack intelligent NoSQL application built to eliminate commercial food waste. By connecting Food Donors (restaurants, banquet halls), Verified Shelters/NGOs, and Volunteer Couriers, the system ensures freshly prepared meals reach hungry communities within safe freshness windows. The platform enforces database-level strict $jsonSchema validation, compound B-tree indexing, atomic double-claim prevention, and six analytical multi-stage PyMongo aggregation pipelines.

1. System Architecture

FoodRescue is built as a modular 3-tier system separating presentation, business logic, and database storage:

  • Presentation Tier (React 18 + Vite): Role-specific portals (Donor, NGO, Volunteer, Admin), interactive SVG visualizations via Recharts, split-screen sliding authentication UI, and printable official certificates.
  • Application Tier (Python Flask + PyMongo): Modular REST API organized with Flask Blueprints, JWT cryptographic verification, and atomic state transitions preventing race conditions.
  • Data Tier (MongoDB 8.0): Six production collections (users, organizations, donations, donation_requests, delivery_tasks, volunteer_profiles) guarded by $jsonSchema constraints and B-Tree indexes.

2. MongoDB Data Modeling & Collections

Collection Key Attributes Design Strategy Primary Index
users name, email, passwordHash, role, phone (+91), address, isActive Normalized Root email (Unique B-Tree)
organizations userId, organizationName, organizationType, serviceArea, verificationStatus Referenced to User userId (Single Field)
donations donorId, foodName, category, quantityKg, preparedAt, availableUntil, dietaryInfo[], status Referenced + Embedded Tags status, availableUntil (Compound)
donation_requests donationId, organizationId, requestedQuantityKg, status, requestedAt Referenced donationId, status (Compound)
delivery_tasks donationId, requestId, volunteerId, status, foodQuantityKg, pointsAwarded Referenced volunteerId, status (Compound)
volunteer_profiles userId, transportType, transportCapacityKg, totalDeliveries, totalPoints, badges[] Referenced + Embedded Badges totalPoints (Descending)

Architectural Decision: Referencing vs. Embedding

Core transactional entities (donations, donation_requests, and delivery_tasks) use Normalized Referencing with ObjectId pointers to prevent unbounded document growth beyond MongoDB's 16 MB limit and avoid write contention during simultaneous claims. Conversely, low-cardinality attributes like dietaryInfo tags and volunteer achievement badges use Denormalized Embedding for fast single-document reads.

3. Concurrency Safety & Double-Claim Prevention

To prevent race conditions where two couriers accept the same delivery task simultaneously, FoodRescue executes atomic find_one_and_update operations directly within MongoDB's engine: 

# Atomic Concurrency-Safe Courier Task Assignment
updated_task = db.delivery_tasks.find_one_and_update(
    {
        "_id": ObjectId(task_id),
        "status": "pending_assignment",
        "volunteerId": None  # Task must be unassigned
    },
    {
        "$set": {"status": "accepted", "volunteerId": current_user["_id"]}
    },
    return_document=ReturnDocument.AFTER
)

if not updated_task:
    return jsonify({"error": "Task was already claimed by another volunteer"}), 409

4. Advanced MongoDB Aggregation Pipelines

Six server-side PyMongo aggregation pipelines power the live analytics and dashboards:

Pipeline Key Stages Analytical Purpose
Pipeline 1: Rescued Trend $match, $project ($dateToString), $group, $sort Historical timeline of verified food rescued (Kg) grouped by date.
Pipeline 2: Top Donors $match, $group, $lookup, $unwind, $sort Total food kilograms contributed per commercial establishment.
Pipeline 3: Volunteer Leaderboard $lookup, $unwind, $sort (totalPoints: -1), $limit Courier rankings based on verified completed rescue missions.
Pipeline 4: Delivered by Courier $match, $group, $lookup, $unwind, $project Cross-verifies volunteer statistics directly from completed tasks.
Pipeline 5: Category & Status $group (multi-key), $project, $sort Matrix breakdown of food categories vs current lifecycle state.
Pipeline 6: NGO Fulfillment $group, $lookup, $unwind, $project ($cond, $divide) Calculates percentage of shelter requests successfully fulfilled.

Sample Pipeline Code: Pipeline 2 (Top Donors via $lookup)

pipeline = [
    {"$match": {"status": {"$nin": ["cancelled"]}}},
    {"$group": {
        "_id": "$donorId",
        "totalDonatedKg": {"$sum": "$quantityKg"},
        "donationsCount": {"$sum": 1},
        "completedRescues": {"$sum": {"$cond": [{"$eq": ["$status", "delivered"]}, 1, 0]}}
    }},
    {"$lookup": {"from": "users", "localField": "_id", "foreignField": "_id", "as": "donor"}},
    {"$unwind": "$donor"},
    {"$project": {
        "_id": 0, "donorId": {"$toString": "$_id"}, "donorName": "$donor.name",
        "totalDonatedKg": {"$round": ["$totalDonatedKg", 2]},
        "donationsCount": 1, "completedRescues": 1
    }},
    {"$sort": {"totalDonatedKg": -1}}
]
